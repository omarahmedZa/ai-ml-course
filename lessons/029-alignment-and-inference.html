Alignment & inference

You can explain SFT → RLHF/DPO, and how context window and temperature shape output.

Why this matters

A pretrained model completes text, including text that argues, lies or refuses. Alignment is the stage that turns it into something that answers requests, and inference settings decide what you get out of it at the moment you ask.

Three stages do the work: supervised fine-tuning on demonstrations, preference optimisation against a learned judge, and then the decoding choices — context window, temperature, cache. Most "the model is being weird" complaints trace to one of them. In an exam, "what does the KL term prevent?" has a one-line answer: drift into regions where the reward model is wrong. In a project, the bug is usually the context window: a 6,000-token prompt sent to a model with a 4,000-token limit, where the oldest part — often the instruction itself — is silently dropped and the model answers a question you did not ask. The second is temperature: setting it to 0 expecting determinism, then failing a test that passed an hour ago on a different machine.

The one core idea

Alignment trains a stand-in judge and then optimises the model against it. The judge is a reward model: a network that reads a prompt and an answer and outputs one number saying how good a human would find it. Training against a stand-in is cheap and scales; it is also the source of every failure in this lesson, because the model will find the gap between the judge and what you actually wanted.

In one line: copy good answers, learn to score answers, then push the score up without drifting too far from the copy. With logits [2, 1, 0], temperature 1 gives probabilities [0.665, 0.245, 0.090]; temperature 0.5 gives [0.867, 0.117, 0.016] — same ranking, far sharper.

How it actually works

Seven parts, from a base model to the token you see on screen.

Part 1 — Supervised fine-tuning on demonstrations

Humans write prompt–answer pairs, typically a few thousand to a few hundred thousand, and the model is trained with cross-entropy on the answer tokens only; the prompt is masked out of the loss. Format matters as much as content: the model learns where an answer starts and when to stop. Why this part exists: a base model has no idea that a question deserves a reply, so without this stage a prompt is just text to continue.

Part 2 — Train a reward model on comparisons

Annotators see two answers to the same prompt and pick the better one. The reward model learns to give the preferred answer a higher score, using the Bradley–Terry loss −log σ(r(A) − r(B)), where σ is the logistic function. Why this part exists: people are unreliable at absolute ratings but consistent at pairwise choices, and a single number is what an optimiser can climb.

Part 3 — Optimise the policy with a leash

PPO, a reinforcement-learning loop, samples answers, scores them with the reward model, and updates the model to raise that score. The objective subtracts β · KL(π ‖ π_SFT), a penalty on drifting away from the fine-tuned model. Why this part exists: the reward model is a rough approximation, so an unconstrained optimiser finds its errors — repetitive, flattering, or confidently wrong text that scores highly.

Part 4 — Or skip the reward model with DPO

Direct preference optimisation uses the same pairs but writes the loss directly on the model's own log-probabilities, so the reward network and the sampling loop disappear. It needs one forward pass per answer instead of an RL rollout. Why this part exists: PPO is expensive and unstable; DPO reaches the same optimum with a classification-style loss.

Part 5 — Respect the context window

The context window is the maximum number of tokens the model can see at once — 4,000 in older models, 128,000 in current ones. Anything beyond it is truncated, and attention cost grows with the square of the length. Why this part exists: without a hard limit, memory would grow without bound; with it, something must be dropped, and the drop is silent.

Part 6 — Turn logits into a token

The model outputs one raw score, called a logit, per vocabulary entry. Divide every logit by the temperature T, apply softmax, then sample from the resulting distribution. T = 1 is the model's native distribution; T → 0 is greedy. Why this part exists: sampling is what makes one prompt produce different text, and the divisor is the only knob that changes the shape without retraining.

Part 7 — Cache the keys and values

Generation is one token at a time. Without a cache, each new token would recompute attention over the whole prefix; with a KV cache, the keys and values of past tokens are stored and only the new row is computed. Why this part exists: generation cost per token drops from growing with the prefix to constant, which is the difference between a usable chat model and an unusable one.

1. Temperature, numerically

Logits [2, 1, 0], three settings. Each row divides the logits, exponentiates, and divides by the sum.

1.0[2, 1, 0]e² = 7.39; e¹ = 2.72; sum 11.11[0.665, 0.245, 0.090]

What to notice. The ranking never changes — the top token is the top token at every temperature, because dividing by a positive number preserves order. What changes is how much of the mass it holds: 87% at 0.5, 51% at 2.0. Low temperature sharpens fluency and collapses diversity; high temperature makes rare tokens likely, including the wrong ones. It cannot add knowledge, because the ranking it samples from is fixed.

2. The reward model's loss on one pair

Two answers, scores r(A) and r(B). Loss is −ln σ(r(A) − r(B)), and the logistic function σ(z) = 1 / (1 + e^−z).

What to notice. Only the difference matters: rows 1 and 4 have identical loss even though every score moved by 3. That is why a reward model's absolute numbers are meaningless and only its ordering is trained. A reversed pair (row 3) costs 0.798 — more than a correct-but-unsure one — and no finite score difference ever reaches zero loss, so the loss keeps pushing the gap wider indefinitely.

The cache costs memory instead: keys and values for every layer and every past token must be stored, which is why a long chat can exhaust GPU memory even though the model itself fits comfortably.

The trap

Most common wrong mental model

"RLHF makes the model more truthful." It feels right because the training signal comes from humans, and humans were asked to prefer accurate answers.

The correction is that RLHF makes the model better at satisfying the reward model, which is a compressed approximation of human judgement. If that approximation rewards confidence, length or agreement, you get more of those — including confident errors. Truthfulness needs verification against something outside the model, not preference optimisation. A second trap is expecting T = 0 to be deterministic: batching, float non-associativity and hardware scheduling change results slightly, so greedy decoding is reproducible on one machine, not across machines.

The tell: the model gets more confident but not more correct — wrong answers arrive in the same fluent, well-formatted shape as right ones, and asking for a source produces a plausible citation rather than a checkable one. The other tell is length inflation: if answers grow steadily longer while accuracy stays flat, the reward model is scoring form rather than content.

Retrieval check

  1. What does the KL term in RLHF actually prevent?
    Answer

    Large drift from the SFT policy. Without it, PPO finds inputs where the reward model is wrong and exploits them, producing degenerate but high-scoring text.

  2. Why does DPO need preference pairs but no reward model?
    Answer

    It derives a loss directly on the policy's log-probabilities that has the same optimum as the preference objective, so the intermediate reward network is not needed.

  3. A model at T = 0.2 repeats itself. What is happening?
    Answer

    Sharpening pushes probability mass onto the single most likely token, so the same phrase recurs. Raising temperature or adding a repetition penalty restores diversity.

Build it in Colab

Runnable, NumPy-only, no setup: open the notebook in Colab · local copy. Sections, plots, sliders and line-by-line notes — run the cells in order, then change one number and rerun.

import numpy as np
def softmax(z):
    e = np.exp(z - z.max()); return e / e.sum()
logits = np.array([2., 1., 0.])
for T in (0.5, 1.0, 2.0):
    print(f"T={T}: {softmax(logits / T).round(3)}")
# DPO-style preference loss on two completions
