Serving & latency

You can read p50, p95 and p99 latency, compute them by hand, and explain why the average hides the requests users complain about.

SystemsSystems

Why this matters— latency

One slow request is what a user remembers. If ninety-nine requests take 40 milliseconds and one takes two seconds, the average still looks fine — and the person who waited is the one who closes the app. Serving is where the clock matters as much as the score.

The failure it prevents. An exam asks "average latency is 70 ms; is the service healthy?" and "yes" misses the point: an average says nothing about the slowest requests, and those time out. A laptop benchmark with one request at a time reports 20 ms while production gives some users half a second.

The one core idea— latency

Latency is not one number. It is a distribution: collect many request times, sort them, and look where the slow ones sit. The p95 is the time 95% of requests beat — one request in twenty is slower.

Throughput is how many requests the service finishes per second. Latency and throughput trade against each other: batching more work raises throughput and usually raises waiting time too.

p95 = the time 95% of requests beat

Report several percentiles, not one average. The tail is where timeouts and complaints live.

How it actually works— latency

Six steps: start the clock correctly, collect samples, sort, take percentiles, watch utilisation, then fix the tail.

Part 1 — Start the clock in the right place

Begin when the request reaches the edge of your system and stop when the last byte of the response leaves. That includes queueing, compute, database calls and network. Timing only the forward pass measures something no user experiences.

Why: most of a slow request is waiting, not arithmetic.

Part 2 — Collect enough samples

Record every request for a fixed window — say ten minutes — and keep the count. A p99 needs a few hundred samples; with 50 requests it is just the slowest one.

Why: percentiles are positions in a list; with too few positions, the one you care about is noise.

Part 3 — Sort the times

Put the millisecond values in ascending order. Now "the slowest 5%" is a region at the right end of the list, and you can point at it. The nearest-rank method needs no distribution maths.

Why: sorting turns a vague question about "slow" into an index you can count.

Part 4 — Take the nearest-rank percentile

For a percentile q and n samples, compute rank = ceil(q / 100 × n) and take the value at that 1-based position. For 20 values, p95 needs ceil(0.95 × 20) = 19, so it is the 19th value.

Why: the rounding rule decides whether p100 is the last value or an error; writing it down keeps two teams consistent.

Part 5 — Watch how busy the server is

Utilisation ρ is the share of capacity in use. As ρ approaches 1, waiting time grows much faster than load. Running at 50–60% leaves room for bursts; 95% turns a small spike into a long queue.

Why: the same model is fast on an idle machine and slow on a busy one.

Part 6 — Fix the tail

Cache repeated work, shrink batches, set timeouts, shed load you cannot serve, and add replicas before the queue forms. Then measure again with the same clock and window.

Why: the average is dominated by fast requests, so improving those can leave the tail untouched.

Worked example— latency

Twenty request times in milliseconds, already sorted:

Step 1 — find the ranks. Half of 20 is 10, so p50 is the 10th value: 45. Ninety-five percent of 20 is 19, so p95 is the 19th value: 150. Ninety-nine percent of 20 is 19.8, which rounds up to 20: 400.

Step 2 — compare mean and tail. The mean is 72.6, below p95. Nineteen fast requests pull it down while the 400 ms one sits far right. Without it the mean would be 1051 / 19 = 55.3, so one request adds about 17 ms.

Step 3 — scale it to a day. At one million requests, 5% beyond p95 is 50,000 and 1% beyond p99 is 10,000 — the requests that hit timeouts, retries and tickets.

What to notice. The p50 says quick, the p99 says not; both are true. A mean hides the 400 ms request.

The trap— latency

Most common wrong mental model

"Our benchmark says 20 ms, so production is fine." It feels right because the number came from the same code. But the benchmark probably ran one request at a time, idle, with no network and no queue — none of which is true for a user.

A second version reports p99 below p95, or averages percentiles across machines — arithmetic that cannot describe one request stream.

Correction: measure end-to-end, publish p50/p95/p99 with sample count and window, and state the load. "p95 = 150 ms over 100,000 requests at 40 per second" is reproducible.

The tell: a latency slide with no percentiles, or a p99 equal to the slowest request on a tiny sample. A benchmark that never mentions concurrency is the second tell — with one client there is no queue.

Retrieval check— latency

  1. You have 100 sorted request times. Which position is p95?
    Answer

    ceil(0.95 × 100) = 95, so the 95th value. Five values are slower, which is the 5% above p95.

  2. How can the mean be 72 ms while p95 is 150 ms?
    Answer

    Most requests are fast and a few are very slow. The many small values pull the mean down while the slow tail sets the high percentiles.

  3. Batching doubles throughput. What usually happens to latency?
    Answer

    It rises, especially at the tail: requests wait for a batch to fill and then to finish. Throughput and latency are a trade.

Solve it · 058 — Nearest-rank percentile, off the end

Build it in Colab— latency

Runnable, NumPy-only, no setup: open the notebook in Colab · local copy. Change the 400 ms request and watch the percentiles move.

import numpy as np
lat = np.array([30, 32, 33, 35, 36, 38, 40, 41, 42, 45,
                47, 50, 52, 55, 60, 70, 85, 110, 150, 400])
for q in (50, 95, 99):
    rank = int(np.ceil(q / 100 * len(lat)))          # 1-based position
    print(f"p{q} = {np.sort(lat)[rank - 1]} ms")    # nearest rank
print("mean =", lat.mean().round(1), "ms")          # for contrast
