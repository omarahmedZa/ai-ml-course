Attention: a soft lookup

You can compute scaled dot-product attention by hand for two tokens and explain the Q/K/V roles.

Why this matters

Attention lets a language model treat a sentence as a web of related positions rather than a fixed row of slots. Each token writes a question, compares that question against every token's advertisement, and copies a blend of what the best matches offer.

It is the only place in a Transformer where information moves sideways between positions; the feed-forward layer, the normalisation and the output head all work on one token at a time. That is why "it" can take its meaning from a noun eight tokens back. In an exam, "compute attention for these two tokens" is four mechanical steps, and the marks sit in the arithmetic. In a project, the same four steps host the quiet bugs: a softmax computed down the columns instead of across the rows, so each key sums to 1 while each query sums to 1.7 and the output arrives 70% too long; or a scale factor left out because the code "looked fine". Both run without error and train badly.

The one core idea

Picture a library desk. You arrive with a question (the query). Every book has a label on its spine (the key) saying what it covers, and pages inside (the value) holding the actual content. You do not pick one book and ignore the rest; you score every label against your question and photocopy a fraction of each book, in proportion to how well its label matched.

In one line: attention is a soft lookup — score everything, then take a weighted average. With q = [1, 0], k₁ = [1, 0], k₂ = [0, 1], the two scores are 1 and 0; after dividing by √2 and exponentiating they become weights 0.670 and 0.330, so the output is 0.670 × v₁ + 0.330 × v₂.

How it actually works

Seven parts. Each one is a line of the formula below, in the order the numbers travel.

Attention(Q,K,V) = softmax( QKᵀ / √d_k ) V
VectorRoleAnalogy
Q (query)What this position is looking forSearch query
K (key)What this position offersDocument title / index
V (value)What this position passes onDocument body

Part 1 — Make three vectors per token

A token arrives as a list of 512 numbers. Three learned matrices multiply that list and produce three new lists: a query, a key and a value, each 512 numbers wide. Why this part exists: a single vector cannot be both the question and the answer — if it were, every token would match itself most strongly and learn nothing about its neighbours.

Part 2 — Score every pair with a dot product

Every query is dotted with every key: multiply matching positions and add. For unit-length vectors the score is 1 when the two point the same way, 0 when they are perpendicular, and negative when they disagree. A 12-token sequence therefore produces a 12×12 score matrix — 144 numbers — and each row belongs to one query. Why this part exists: this matrix is the only quantity that decides who listens to whom; every later step merely smooths and applies it.

Part 3 — Divide by √d_k

With head width d_k = 64, the raw scores of random unit vectors have a standard deviation of about 8, so ordinary entries sit near ±8. Dividing by √64 = 8 pulls the spread back to roughly 1. Why this part exists: softmax over scores of size 8 puts 0.9997 of the mass on one token, and the gradient through a vector with all its mass on one entry is almost exactly zero, so the layer stops learning.

Part 4 — Softmax each row

Per row: subtract the row maximum, exponentiate every entry, then divide by the row sum. Scores 0.707 and 0 become e⁰·⁷⁰⁷ = 2.028 and e⁰ = 1; the total is 3.028, so the weights are 0.670 and 0.330. Why this part exists: weights must be positive and add to 1, otherwise the output is a sum that grows with sequence length instead of an average that stays in the values' own range.

Part 5 — Blend the values

The output for that query is 0.670 × [10, 0] + 0.330 × [0, 10] = [6.70, 3.30], still two numbers wide. Every query repeats this independently, so the layer returns one vector per token, shape n × d. Why this part exists: the next layer needs an input of the same width, and mixing values rather than scores is what lets one position carry content from several neighbours at once.

Part 6 — Run several heads

Rather than one 512-wide attention, the block runs 8 heads of 64 dimensions each, concatenates the eight outputs back to 512, and multiplies by an output matrix. The multiply count is the same as a single wide head. Why this part exists: one softmax per layer can express only one averaging pattern, so a head tracking syntax would have to share weights with one tracking coreference.

Part 7 — Pay for the square

The score matrix costs n² entries per head. At n = 1,000 that is 1,000,000 numbers per head, or 8,000,000 across 8 heads; at n = 2,000 it is 4,000,000 per head. Why this part exists: this quadratic term, not the parameter count, sets the price of long context.

Worked example

1. Two tokens, by hand

Query q = [1, 0]; keys k₁ = [1, 0], k₂ = [0, 1]; values v₁ = [10, 0], v₂ = [0, 10]; d_k = 2. Every multiplication is written out.

What to notice. Token 1 matched perfectly, yet it takes only 67% of the output, because a softmax of two scores can never reach 100%. That split comes from the score gap after scaling, not from the data. Remove the √2 and the gap stays 1, giving e¹ = 2.718 against 1, weights 0.731 and 0.269 — a different output from the same inputs.

2. Why the divisor is √d_k and not d_k

Take one score gap of 8, which is one standard deviation at d = 64, and compare the two candidate divisors.

VersionArithmeticWeights
No scaling, scores [8, 0]e⁸ = 2,981; e⁰ = 1; sum 2,982[0.99966, 0.00034]
Scaled by √64 = 88 ÷ 8 = 1; 0 ÷ 8 = 0 → [1, 0][0.731, 0.269]
After softmax on [1, 0]e¹ = 2.718; e⁰ = 1; sum 3.718[0.731, 0.269]

What to notice. Scaling changes confidence but never the ranking: the winner is the same in both rows. The unscaled version has already decided: a slightly larger gap rounds to exactly 1.0 and 0.0 in 32-bit floats, and the gradient, proportional to p(1 − p), rounds to zero. Dividing by d_k instead would over-correct: a gap of 8 becomes 0.125, the weights become 0.531 and 0.469, and every head averages almost everything.

What to notice. Doubling the sequence multiplies the work by four, not two. Each entry is also kept in memory for the backward pass, so the same factor applies to activations: a context that fits in 8 GB at 1,000 tokens needs roughly 32 GB at 2,000.

The trap

Most common wrong mental model

"The attention weights show why the model gave that answer." It feels right because weights are the one set of numbers in the block that sum to 1 and read like percentages.

The correction is that a weight is a routing decision for the next layer, not a causal contribution to the output. A token can receive a weight of 0.8 and add nothing, because its value vector is close to zero; and the feed-forward layer that follows can ignore whatever arrived. Attention heads are also redundant: ablating a single head often leaves the prediction unchanged. Topic 32 shows this empirically.

A related error is expecting memory or recurrence. Attention has neither — it re-reads the whole prefix on every pass, and order has to be injected explicitly (topic 27).

The tell: replace the highest-weighted token's value with zeros and rerun. If the output barely moves, the weight was routing, not explaining. The second tell is instability: two seeds trained on the same data give different attention maps with the same accuracy — a real explanation would not move.

Retrieval check

  1. Why divide by √d_k rather than by d_k?
    Answer

    A dot product of d independent terms has variance proportional to d, so its standard deviation grows like √d. Dividing by √d normalises the standard deviation, not the variance.

  2. In self-attention, where do Q, K and V come from?
    Answer

    All three are learned linear projections of the same input sequence — three different weight matrices applied to the same tokens.

  3. Why is attention cost quadratic in sequence length?
    Answer

    Every token scores against every other token, producing an n × n matrix. Doubling n quadruples both computation and memory.

Build it in Colab

Runnable, NumPy-only, no setup: open the notebook in Colab · local copy. The cell prints numbers, not pictures — change one value and rerun to see what breaks.

import numpy as np
def softmax(z):
    e = np.exp(z - z.max(axis=-1, keepdims=True))
    return e / e.sum(axis=-1, keepdims=True)
Q = np.array([[1., 0.]])
K = np.array([[1., 0.], [0., 1.]])
V = np.array([[10., 0.], [0., 10.]])
