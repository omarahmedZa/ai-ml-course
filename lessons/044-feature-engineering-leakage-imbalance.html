Feature engineering, leakage & imbalance

You can name the moment a feature becomes available, spot leakage in a pipeline, and choose a metric that survives a 2% positive rate.

Classical MLClassical ML

Why this matters— features

The model is usually the easy part. What decides whether a fraud system works is whether "number of failed logins in the last hour" exists as a column, whether it is computed from data available before the transaction, and whether anyone reports recall instead of accuracy. Feature work sets the ceiling; evaluation tells you whether you reached it. Both fail quietly, which is why they deserve their own lesson.

The failure it prevents. A team predicts loan default with "date the account was closed" in the table. Training accuracy is 96% and launch is approved; in production nothing closes before the decision, so the column is empty and the model is a coin flip. The second is arithmetic: with 2% positives, always saying "no" scores 98% and catches nothing.

10%precision of the example model below
50%recall of that same model

The one core idea— features

A feature is a promise: this number will be computable, the same way, at the moment a prediction is needed. Every statistic used to build it — a mean, a category rate, a scaler's standard deviation — has to be learned from training data only. And when the positive class is rare, the metric has to price the rare class, because accuracy mostly measures the majority.

In one line: ask "could I have known this before the outcome?" and "does this score move when I catch the thing I care about?" The first question catches leakage; the second catches the accuracy trap.

available before the label → fitted on train only

A feature that fails either test will produce a beautiful offline number and a useless system.

How it actually works— features

Part 1 — Features that exist at decision time

Start with the timestamp of the decision and ask what is known at that instant. "Days since last purchase" is available; "days until next purchase" is not. "Account closed date" is available only if the account closed earlier. The same rule covers aggregates: a customer's average spend over the previous 30 days is fair, while their average over the whole dataset includes the future.

Useful transforms are usually simple: one-hot encode categories, bucket a long-tailed count, split a timestamp into hour and weekday, add ratios such as spend per order, and count prior events. Each one must be reproducible from the raw record.

Part 2 — Leakage is a pipeline bug

Any step that learns a number from rows must be fitted on training rows and then applied unchanged. That includes imputation values, scaler means and standard deviations, one-hot vocabularies, target-encoding rates, feature selection, and PCA rotations. Put them in a pipeline so the same frozen object transforms validation, test and production.

The split itself needs care. Random rows leak when one customer contributes many rows: the same person appears in train and test, so the model recognises them. Split by group — customer, patient, device. For time series, split by date, never at random, or the model trains on tomorrow to predict yesterday.

Part 3 — Read the confusion matrix first

With 1 as the positive class, four counts cover every prediction: true positives TP, false positives FP, false negatives FN, true negatives TN. From them:

accuracy = (TP + TN) / n · precision = TP / (TP + FP) · recall = TP / (TP + FN)

Precision answers "when the model says positive, how often is it right?" Recall answers "of the real positives, how many did it find?" F1 is their harmonic mean, 2PR / (P + R), which is low if either one is low. Accuracy appears first only because it is familiar; it is the least informative of the four when the classes are uneven.

Part 4 — Imbalance and the metric that survives it

Imbalance is not a property of the algorithm; it is a mismatch between the base rate and the cost of mistakes. Class weights tell the loss that a missed positive costs more; resampling changes the training rows. Do both inside the training fold only, never before the split, or synthetic positives leak into validation.

Report precision and recall at the threshold you will deploy, plus a threshold-free summary such as PR-AUC (area under the precision–recall curve). ROC-AUC stays optimistic under extreme imbalance because the false-positive rate divides by a huge TN. Finally, choose the threshold from costs: a fraud review team can handle 100 alerts a day, so pick the cutoff that yields 100.

Worked example— features

1. One thousand rows, twenty positives

A model flags 100 transactions. Of those, 10 are fraud; of the 20 real frauds, 10 are missed. The rest are legitimate and mostly cleared, giving TN = 890.

QuantityArithmeticValue
Accuracy(10 + 890) / 100090%
Precision10 / (10 + 90)10%
Recall10 / (10 + 10)50%
F12(0.10)(0.50) / 0.600.167

Read it as a sentence. Nine times in ten the model is right, which sounds excellent until you notice that 90 of its 100 alarms are false. It finds half the fraud and wastes 90 reviews. A model that says "legitimate" to everything scores 98% accuracy, has recall 0, and cannot compute precision because it raises no alarms — the 98% is a statement about the majority, not about fraud.

Now compare two thresholds. Lowering the cutoff to catch 18 of 20 frauds might raise FP to 300: recall becomes 90%, precision 18/318 = 5.7%. Raising it to 20 alarms might catch 6: precision 30%, recall 30%. Neither is better in the abstract; review capacity decides.

2. Target encoding that memorises

Replace a category with its mean target. A rare category "A" appears once, with y = 1, so its encoded value is 1.0 — the label itself. A tree splits on that column, and on training data the split is perfect. The feature has learned nothing that transfers.

Smooth it. Blend the category mean with the global mean 0.2, using strength m = 10:

StepArithmeticValue
Smoothed encoding(1 × 1 + 10 × 0.2) / (1 + 10)0.273
Same category, 100 rows(30 + 2) / 1100.291

Read it as a sentence. One observation pulls the estimate only a little away from 0.2; a hundred observations are trusted almost fully. Smoothing is not a fix for leakage on its own — the encoding still has to be computed out-of-fold — but it stops a single row from becoming a perfect feature.

The trap— features

Most common wrong mental model

"98% accuracy means the model works." Accuracy is the share of all rows answered correctly, and with a 2% positive rate the all-negative model already owns 98%. The number is dominated by the majority class, so it can rise while the model gets worse at the only thing you care about.

It feels right because 98% sounds like an A. But a metric that barely moves when you catch a fraud is not measuring fraud; the confusion matrix shows TP = 0 while accuracy looks healthy.

Correction: report the base rate, the confusion matrix, precision, recall and PR-AUC at the deployed threshold. Then check the split: was every transform fitted on training rows only, and were rows grouped by customer and ordered by time?

The tell: accuracy near the base rate of the majority class, zero true positives, or a test score that jumps when a column is removed. For leakage, the tell is a feature whose importance is implausibly high and whose values would be missing at prediction time.

Retrieval check— features

  1. You scale features before splitting into train and test. What is wrong, and what is the fix?
    Answer

    The scaler's mean and standard deviation were computed from test rows, so information crossed the boundary. Fit the scaler on training rows, then apply that frozen transform to test rows and production.

  2. A fraud model has recall 0.9 and precision 0.06. Describe what it does in one sentence.
    Answer

    It catches 90% of fraud but only 6% of its alerts are real, so the review team spends most of its time on false alarms. That may still be the right trade if a miss is expensive and reviews are cheap.

  3. Why can ROC-AUC look strong when the positive class is 1% of the data?
    Answer

    The false-positive rate divides by the large negative count, so a model can accumulate many false positives while the rate stays small. Precision divides by the alerts raised, which is why PR-AUC exposes the problem.

Build it in Colab— features

Runnable, NumPy-only: open the notebook in Colab · local copy. It builds a confusion matrix, computes four metrics, and demonstrates smoothed target encoding.

import numpy as np
tp, fp, fn, tn = 10, 90, 10, 890                 # counts from the example
precision = tp / (tp + fp)                       # 0.10
recall = tp / (tp + fn)                          # 0.50
f1 = 2 * precision * recall / (precision + recall)  # 0.167
accuracy = (tp + tn) / (tp + fp + fn + tn)       # 0.90
print(accuracy, precision, recall, round(f1, 3))
