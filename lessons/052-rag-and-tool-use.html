RAG & tool use

You can explain how retrieval fills the context window and how a tool call becomes an action, including what each one can break.

Language & TransformersNLP & Transformers

Why this matters— the interface

After training, a model's weights are frozen. It cannot learn your refund policy, see today's orders, or send email unless something puts that information in front of it. Two mechanisms do it. Retrieval-augmented generation (RAG) finds relevant text and writes it into the prompt. Tool use lets the model emit a structured request that outside code executes.

The failure it prevents. A support bot is asked about a refund after 45 days. Without help it invents a plausible 30-day policy, because the text is not in its weights. With retrieval, the real clause enters the context; with a tool, the bot can check the order date. The language ability was never the problem.

The one core idea— the context

The context window is the model's only writable memory at inference. Everything it knows about your question is in the tokens in front of it. RAG and tool use are two ways of choosing those tokens well: RAG chooses documents, tools choose observations from outside. Neither changes the weights.

In one line: retrieve what is relevant, fit it in the budget, and let the model cite or call — not guess. Retrieval is a ranking problem followed by a packing problem; tool use is a parsing and permission problem around a function call.

context = top-k chunks, packed to fit B tokens

Rank by similarity, then admit chunks in order until the budget is spent. Relevance without a budget check overflows the window.

How it actually works— the loop

Six parts: four for retrieval, two for tools.

Part 1 — Chunk the documents

Split each document into passages of roughly 300–500 tokens, with a little overlap so a boundary sentence survives whole. Store source and position with every chunk. A whole manual blurs in one vector; a lone sentence loses the context that makes it true.

Part 2 — Embed the query and the chunks

An embedding maps text to a vector of numbers, placing similar meanings close together. Embed chunks once, offline; embed the query at request time. Comparing vectors is arithmetic; comparing meanings in text is not.

Part 3 — Rank by cosine similarity

Cosine measures the angle between vectors and ignores length: cos = (a · b) / (‖a‖‖b‖), from −1 to 1. Take the top k, usually 3 to 10. It gives a cheap, sortable relevance score for every chunk.

Part 4 — Pack the chunks into the token budget

Count tokens, not words. From the window, subtract system prompt, question and answer reserve, then admit ranked chunks until the remainder is spent. Skip a chunk that does not fit; never truncate mid-sentence. Overflow silently drops the oldest tokens, often the instruction.

Part 5 — Make the answer checkable

Instruct the model to cite a chunk id per claim and to say "not in the provided documents" when the chunks do not answer. A citation is a pointer you can verify; a confident sentence is not.

Part 6 — Wrap every tool in a validator

Publish a schema per tool; the model emits a call; your code checks the tool is allowed, fields are present, values are within limits, and the user has permission. Execute, append the result, continue. The model proposes; your code decides.

Worked example— the arithmetic

1. Ranking three chunks

Query vector q = [0.6, 0.8]. Three unit-length chunks: A [0.6, 0.8], B [0.8, 0.6], C [−0.6, 0.8]. Because every vector has length 1, the cosine is just the dot product.

What to notice. A and B are nearly tied at 1.00 and 0.96, so returning only the top 1 drops a chunk almost as relevant as the winner. C is still positive at 0.28 — cosine has no threshold meaning "irrelevant".

2. Fitting the budget

Window 2,000 tokens. System prompt 250, question 50, answer reserve 600. That leaves 2,000 − 250 − 50 − 600 = 1,100 tokens for chunks. Ranked chunks are A 400, B 500, C 300, D 200.

3. One tool call

The model emits {"tool": "refund", "args": {"order": "A17", "amount": 40}}. The validator checks the tool is allowed, amount is a number, and 40 ≤ 100, the per-call limit. All pass, so the API returns {"status": "ok", "refunded": 40}, which is appended and becomes the reply. An amount of 400 would fail and never reach the API.

The trap— the seam

Most common wrong mental model

"RAG grounds the model, so it cannot hallucinate." Retrieval changes the prompt, not the model. If the right chunk is missing, the model answers from its weights in the same fluent voice; if the chunk is present but ambiguous, it can still misread it.

It feels right because the answer cites a source, and a citation looks like evidence. But the citation is generated text too: the model can attach a real chunk id to a claim that chunk never makes.

Correction: measure retrieval separately from generation. Recall@k asks whether the needed chunk reached the context; faithfulness asks whether the answer is supported by what was retrieved. A generation fix cannot repair a retrieval miss.

The tell: the answer cites document 3, and document 3 does not contain the quoted sentence. The second tell is an ablation: set k = 0 and the answer barely changes, meaning the chunks were never used. A third is a question answered in chunk 9 while k = 5.

Retrieval check— recall

  1. Why is cosine preferred to raw dot product for chunk ranking?
    Answer

    It divides out both lengths, so a long chunk is not favoured for its norm. It compares direction — meaning — not magnitude.

  2. Your budget allows 1,000 tokens and the top chunk is 1,200. What should happen?
    Answer

    Skip it and try the next chunk, or split it during chunking. Truncating loses the end of the claim; sending it overflows the window.

  3. Where must a tool call be validated — in the prompt or in code?
    Answer

    In code. The prompt can ask for valid arguments, but only a parser and permission check outside the model can guarantee that nothing dangerous executes.

Solve it · 052 — Context budget

Build it in Colab— the notebook

Runnable, NumPy-only: open the notebook in Colab · local copy. It scores chunks with cosine and packs them into a budget you can change.

import numpy as np
q = np.array([0.6, 0.8])
chunks = {"A": np.array([0.6, 0.8]), "B": np.array([0.8, 0.6]), "C": np.array([-0.6, 0.8])}
for name, v in chunks.items():
    cos = q @ v / (np.linalg.norm(q) * np.linalg.norm(v))
    print(name, round(float(cos), 2))       # A 1.00, B 0.96, C 0.28
