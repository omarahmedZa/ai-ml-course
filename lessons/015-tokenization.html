Tokenization: text → integers

You can explain vocabularies, subwords, OOV, and why token count is not word count.

Why this matters

A tokenizer is the first component to touch text in any language model, and the last one most people check. It maps a string to a list of integers drawn from a fixed table. Everything downstream — the embedding lookup in topic 16, the attention window, the price on an API bill — is measured in those integers, so a tokenizer error surfaces as a modelling error three layers away.

Here is the exam version of that failure. A corpus of 900,000 English words must fit a 1,000,000-token budget. Words are fewer than tokens, so the naive answer is yes, with room to spare. The real count is 900,000 × 1.3 = 1,170,000 tokens, and the last 130,000 words never reach the model. In a project the same arithmetic appears as a loader that chunks by character count and cuts a JSON object in half.

The one core idea

Picture a shelf of 50,257 pre-printed labels. The tokenizer invents nothing: it chops text into pieces that already sit on the shelf, then hands back the label numbers. A shelf of whole words would need millions of slots and would still miss tomorrow's product name. A shelf of single letters is tiny, but each label says almost nothing on its own. Subwords are the compromise — common words get one label, rare words get assembled from two or three familiar ones.

In one line: the vocabulary is frozen before training, and unseen text is decomposed rather than rejected. The word playgrounds can arrive as three pieces — play, ground, s — which is three integers out of a shelf of 50,257, and the model keeps a usable vector for each piece.

How it actually works

Seven parts, in the order they were invented. Each one plugs a hole that the previous one leaves open.

Part 1 — Fix a vocabulary, then freeze it

A vocabulary is a list of token strings, each with a permanent integer ID; the tokenizer is the function from text to those IDs. Modern models use 32,000 to 100,000 entries, and GPT-2 used 50,257. The list is built once from a sample corpus and never edited afterwards. Why this part exists: if the table changed between training and serving, ID 371 would point at a different piece, and every weight learned for it would be applied to the wrong thing.

Part 2 — Start from characters, not words

Training begins with a tiny alphabet: 256 byte values for byte-level BPE, or roughly 100 characters if you stay inside one writing system. Vowels, punctuation and accented letters each get an ID at this stage. English has more than 500,000 distinct word forms once names and typos are counted, which is why a character start is affordable and a word start is not. Why this part exists: with a character alphabet no input is ever unrepresentable, so the out-of-vocabulary failure cannot occur.

Part 3 — Merge the most frequent adjacent pair

Count every adjacent pair of symbols across the corpus, take the pair that occurs most often, and replace it with one new symbol. Repeat. The early merges are dull — t+h, then e+s — and by merge 32,000 the winners are whole words. Why this part exists: every merge shortens the encoded sequence, and that is what takes a 1,000-word document from about 5,700 characters down to 1,300 integers.

Part 4 — Encode by replaying the merge list

Encoding new text means applying the same merges in the same order, greedily, left to right. Nothing is counted at inference time; the ordered merge list is the entire algorithm. A 12-character word such as unbelievable lands in 3 pieces, and English averages about 4 characters per token. Why this part exists: a deterministic order guarantees that one sentence always produces one sequence of IDs, so caching, batching and replay stay consistent.

Part 5 — Reserve special tokens

Four structural symbols live in the vocabulary and never come from raw text: <bos> opens a sequence, <eos> closes it, <pad> fills short rows in a batch, <mask> hides a position during training. To the model they are ordinary IDs. Why this part exists: batching requires equal-length rows, and without a dedicated filler the model would treat padding characters as content and learn from them.

Part 6 — Budget in tokens, not words

Context limits and cost are both counted in tokens: 1,000 English words is about 1,300 tokens, the same 1,000 words of source code about 1,700, and 1,000 words of base64 or file hashes about 4,000. The rule of thumb is 4 characters per token, so 1 token is roughly 0.75 words. Why this part exists: a 4,000-token window holds 3,077 words of prose but only 1,000 words of a hash dump, and mixing the two units truncates the second without any error message.

Part 7 — Ship the tokenizer file with the model

The merge list, the vocabulary and the normalisation rules are saved as a configuration of a few megabytes and loaded at inference. Fine-tuning on text tokenized by a different release silently renumbers every input. Why this part exists: two tokenizers with identical vocabulary sizes can still split the same word differently, and a mismatched split is invisible to code that only checks tensor shapes.

So a word-count estimate is never off by a rounding error, only by a factor — and the factor is not knowable from the word count alone. The base64 row consumes the window exactly, so a single extra token truncates the file. Same length, three different bills.

The trap

Most common wrong mental model

"A token is a word." It feels right because for short, ordinary sentences it nearly holds: 1,000 words of prose is 1,300 tokens, and 0.75 words per token looks like rounding rather than a ratio.

The correction is that the ratio is not a constant. It moves from 1.3 on prose to 4.0 on hashes, so any estimate built on len(text.split()) is wrong by a factor, never by a percentage. The same misconception has a second face: expecting the model to see letters. It receives IDs, so "how many r's in strawberry" asks about a representation that does not exist inside the model.

The tell: a chunker whose cut points drift as documents change, or a token budget that is fine in testing and 30% over in production once users paste code. The sharpest tell is behavioural: the model discusses a word fluently but cannot say how it is spelled, because the letters were never available to it. If two runs of the same prompt bill different token counts, the tokenizer configuration changed between them.

Retrieval check

  1. Why does word-level tokenisation fail on medical text?
    Answer

    The vocabulary cannot contain every drug name and abbreviation. Unseen terms collapse to <UNK>, erasing distinctions the model needs — including negation and dosage.

  2. A 128k-token context holds roughly how many English words? What about lines of code?
    Answer

    Roughly 95,000 words of prose (÷1.3), but far fewer lines of code — code runs nearer 1.7 tokens per word, and identifiers fragment further.

  3. What does BPE actually merge, and in what order?
    Answer

    The most frequent adjacent pair of symbols, repeatedly, starting from characters. Frequency decides order, which is why frequent words end up as single tokens.

Build it in Colab

Runnable, NumPy-only, no setup: open the notebook in Colab · local copy. The cell prints numbers, not pictures — change one value and rerun to see what breaks.

from collections import Counter
corpus = "low lower lowest newer newest wider widest"
words = [" ".join(w) + " </w>" for w in corpus.split()]
print("start:", words[:3])
vocab = Counter()
for w in words:
    vocab.update(w.split())
