Federated learning & FedAvg

You can describe the round protocol, write the averaging rule, and justify data locality.

Why this matters— FedAvg

Federated learning is how you train when the examples cannot be collected in one place: a phone keyboard that improves without uploading your messages, a hospital network that shares a tumour model but never the scans, a bank consortium that shares a fraud detector but never transactions. The data stays with its owner; only the model's numbers travel.

In an exam the question is almost always one round of averaging — three clients hold 100, 200 and 700 examples, their local weights are 0.10, 0.50 and 0.90, so what is the new global weight? Equal averaging writes 0.50 and loses the marks; the weighted answer is 0.74. In a project the same mistake is one line, np.mean(client_weights), sitting in the aggregation step. Training runs, the loss curve falls, and the client that owns 70% of the data quietly receives a model that has stopped listening to it.

The one core idea— FedAvg

Picture a class where the teacher may not collect the homework. Each student marks their own work at home, and the teacher averages the sheets into one master copy that everyone uses next week. The master copy is never exactly right for any single student, but it is close for the class, and no exercise book left the house.

In one line: the model is a list of numbers, each client pulls those numbers toward what its own data prefers, and the server replaces them with the evidence-weighted average. Weights 0.10, 0.50 and 0.90 from clients holding 100, 200 and 700 examples give 0.1(0.10) + 0.2(0.50) + 0.7(0.90) = 0.74.

w_{t+1} = Σ_k (n_k/n) w_t^k

Each client trains locally, then the server replaces the weights with an example-weighted average: 700 examples speak seven times louder than 100.

How it actually works— FedAvg

One round is six steps. Keep each client's example count in view throughout; it decides how loudly that client speaks.

Part 1 — Start from one shared model

The server initialises a global parameter vector w_0, perhaps 1,000 numbers, and fixes a round budget such as 100. Every client starts this round from that exact list, not from last week's private copy.

Why this part exists: averaging only means something if the things averaged are comparable; a client starting at round 40 and one starting at round 3 would mix two different models.

Part 2 — Sample a few clients

Of 1,000 registered devices the server contacts a fraction, commonly 10%, so 100 clients work this round. Availability comes in bursts — phones charge overnight, hospital servers batch nightly.

Why this part exists: waiting for all 1,000 means the round never closes, and sampling caps the cost at 100 uploads instead of 1,000.

Part 3 — Send the weights down

The server ships w_t, roughly 1 MB per million parameters stored as 4-byte floats, and each client holds it beside its own rows. No row travels now or later.

Why this part exists: this download is the whole setting; if the server asked for rows instead, the legal reason for the deployment would vanish in a single request.

Part 4 — Train locally for E epochs

Each client runs E passes of SGD, usually 1 to 5, over its own data and produces w_t^k. With 700 examples and E = 5 that is 3,500 example-gradients computed on the device.

Why this part exists: without local steps you have federated SGD, which needs hundreds of rounds; local work is the only lever that turns cheap computation into saved bandwidth.

Part 5 — Upload parameters, never rows

Clients return w_t^k or the delta w_t^k − w_t, still about 1 MB. At 1 Mbps one such upload takes 8 seconds, per client, per round.

Why this part exists: the server must improve the model from numbers whose size does not grow with the number of rows the client holds.

Part 6 — Average by share, then repeat

The server computes w_{t+1} = Σ_k (n_k/n) w_t^k, where n is the total example count. The shares are non-negative and sum to 1, so the result is a convex combination and cannot leave the range spanned by the clients. It broadcasts the result and the loop restarts.

Why this part exists: a 700-example client has a lower-variance gradient than a 100-example one and should count seven times more; equal shares let a tiny client outvote the data.

3. The communication bill

Cost per round is clients times megabytes; the total is rounds times that.

QuantityArithmeticResult
One round, 1,000 clients1,000 × 1 MB1 GB

Server at 100 Mbps100,000 MB ÷ 12.5 MB/s8,000 s ≈ 2.2 h
Same run, 10 clients per round100 × 10 × 1 MB1 GB

What to notice. Sampling a tenth of the clients cuts the bill by 90% without changing the algorithm's shape, which is why partial participation is standard rather than an optimisation. Centralised training moves the dataset once; this run moves 100 GB. Every extra local epoch is an attempt to buy back one of those rounds.

The trap— FedAvg

Most common wrong mental model

"FedAvg is the same as training on the pooled data." It feels right because the formula is what you would write for one model trained on the union of the datasets, and under identical client distributions with a single local step it is literally equivalent.

The equivalence dies twice. Several local steps make each model a function of its own order of data, so averaging models is not averaging gradients. And with heterogeneous data the clients optimise different objectives, so the average can be worse than every client's own model — the drift of topic 34. A second trap hides behind it: assuming a server that sees only updates has solved privacy. An update is a function of the rows that produced it.

Correction: read FedAvg as one approximate step on a reweighted objective, repeated — not as pooled training.

What it feels likeWhat is true
FedAvg is training on the pooled data.It is one approximate step on a reweighted objective; several local steps and non-IID clients break the equivalence.

The tell: a report showing federated accuracy just below centralised accuracy and calling the gap "implementation noise". If the gap widens as you raise E from 1 to 20, it is drift. The second tell is an aggregation line using np.mean while clients have wildly different example counts; check that the shares sum to 1 and ask whether the largest client dominates the result.

Retrieval check— FedAvg

  1. Two clients: 900 examples with local loss optimum 0.2, 100 examples with optimum 0.8. What does one FedAvg round produce?
    Answer

    0.9(0.2) + 0.1(0.8) = 0.26. The global model lands near the large client and largely ignores the small one — the source of fairness complaints in FL.

  2. Why is communication, not computation, the binding constraint?
    Answer

    Clients are often on mobile networks with limited upload bandwidth, and there may be millions of them. Local compute is comparatively cheap and parallel.

  3. What exactly does the server receive from a client?
    Answer

    Model weights or weight updates — never raw examples. That is the defining constraint, and also why privacy is not automatic.

Build it in Colab— FedAvg

Runnable, NumPy-only, no setup: open the notebook in Colab · local copy. Sections, plots, sliders and line-by-line notes — run the cells in order, then change one number and rerun.

import numpy as np
clients = [(100, 0.10), (200, 0.50), (700, 0.90)]
total = sum(n for n, _ in clients)
weighted = sum(n * w for n, w in clients) / total
equal = np.mean([w for _, w in clients])
print(f"weighted FedAvg: {weighted:.3f}  (equal weighting: {equal:.3f})")
