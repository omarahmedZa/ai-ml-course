Seq2seq & encoder–decoder

You can explain translation as encode-then-decode, and state the alignment problem attention solves.

Why this matters

Encoder–decoder is the shape of every generative system you will use: translation, summarisation, speech-to-text, optical character reading, chat. One half reads, the other half writes, and they meet at a single vector. The decoder in a 2014 translation model and the decoder in a chat model are the same object with different plumbing.

A summariser is trained on 100-token news snippets and deployed on 600-token reports. The output stays fluent and loses the headline, because the encoder compressed the first paragraph into the same 512 numbers it uses for everything else and the decoder never sees the input again. On an exam the same gap shows up as "what is teacher forcing, and what problem does it create?" — a question you cannot answer if you think generation works the way training does.

The one core idea

A translator reads the whole page, closes the book, and writes the translation from memory. That is the architecture, not a simplification of it: the encoder's last state is the book, and everything written afterwards is reconstructing a page from a summary. A better translator is not allowed to reopen the book — only a longer memory would help.

In one line: everything the decoder knows arrives through one vector, so a 40-token sentence gives it 12.8 numbers per token and a 400-token one gives it 1.28. The second case is not slower or less accurate in some vague sense; it is arithmetically short of room.

How it actually works

Seven parts: three for reading, three for writing, one for the patch that arrives later.

Part 1 — Encode without emitting

The encoder runs an RNN over x₁ … x_n and throws away every intermediate output, keeping only the final state h_n. For a 40-token sentence that is 40 forward passes and one vector kept. Why this part exists: the input and the output have different lengths and different vocabularies, so the reading half must produce something fixed-size that the writing half can start from.

Part 2 — Pass one context vector across the gap

h_n is the entire channel between the two halves — 512 numbers, whatever the input length. The decoder's first hidden state is initialised from it directly. Why this part exists: without a shared starting state the decoder is an unconditioned language model, fluent and irrelevant, writing plausible sentences that have nothing to do with the input.

Part 3 — Decode one token at a time

At step t the decoder consumes the previous token's embedding plus its own state and produces one score per vocabulary entry — 50,000 scores for a 50,000-token vocabulary. The highest score becomes y_t, and y_t becomes the next input. Why this part exists: output length is unknown in advance, so the model must be able to run for as long as it takes to emit a stop symbol.

Part 4 — Bracket the output with start and stop symbols

<bos> gives the decoder a legal first input, and <eos> gives it a legal way to finish. Both are ordinary vocabulary entries learned during training. Why this part exists: without a learned stop condition the decoder either runs to a hardcoded maximum or halts on a punctuation heuristic.

Part 5 — Train with the true previous token

Teacher forcing feeds the ground-truth y_{t−1} instead of the model's own guess, so all m positions can be scored in one pass: 30 predictions at once for a 30-token target. Why this part exists: sequential training would make a 30-step decoder cost 30 forward passes per example, and early in training the model's own guesses are noise, so it would learn from garbage.

Part 6 — Generate from your own output, and watch it drift

At inference the true token does not exist, so the model consumes its own prediction; greedy decoding takes the top score, beam search keeps the best 5 partial sequences. At 95% per-token accuracy, a 30-token output is fully correct with probability 0.95³⁰ = 0.215. Why this part exists: the mismatch is unavoidable, and knowing its size is what tells you whether to widen the beam or shorten the output.

Part 7 — Let the decoder look back

Attention scores every encoder state against the current decoder state, softmaxes the n scores, and uses the weighted sum as extra input. For a 600-token source that is 600 weights per output step instead of one fixed vector. Why this part exists: alignment. A German verb at the end of the clause must attach to an English verb near the start, and no single summary vector knows which input position the current output word needs.

1. The compression problem, by volume

What to notice. Each row is 512 divided by the token count: 512 ÷ 120 = 4.27, and 512 ÷ 600 = 0.85. Going from the first row to the third is a 75-fold increase in input over a state that never grew, so the model is asked to store less than one number per token. Nothing is broken in the code at that point — the information was discarded at the entrance, and no amount of decoder capacity can recover it.

2. Why an error is not a small error

Assume the model is right about each token with probability 0.95, and one wrong token becomes the next input.

What to notice. A per-token accuracy of 95% sounds like a solved problem and produces a fully correct 50-token answer only 7.7% of the time. The drop from 60% to 8% is not caused by the model getting worse; it is compounding, because every error changes the input for the next step. This is why metrics that score whole sequences are harsh, and why a model can look excellent per token and unusable per sentence.

The 200-token job takes twenty times the 10-token job for the same reason a loop does, and adding GPUs does not shorten a loop whose iterations depend on each other.

The trap

Most common wrong mental model

"The decoder can look at the input while it writes." It feels right because the name says encoder–decoder, as if two halves share a workspace, and because attention in a modern transformer does exactly that.

The correction: in the 2014 architecture the decoder holds h_n and nothing else. Attention is the later patch that reopens the channel, which is why a model with attention translates long sentences better while using the same decoder. And a transformer is a different implementation of this same contract — attention replacing recurrence — not a different idea, so "seq2seq means transformer" is backwards.

The tell: change only the beginning of the input and watch the first few output tokens. If they barely move, the model is writing from a summary that has already averaged the start away. A second tell is a summary that is fluent and vague in equal measure — correct grammar, no names, no numbers — which is what reconstruction from 512 numbers looks like when the source was 600 tokens. If your training loss is fine and your generations degrade after the first wrong word, the gap is exposure bias, not capacity.

Retrieval check

  1. Why does a longer input sentence hurt a vanilla seq2seq model more than a shorter one?
    Answer

    All information must pass through one fixed-size vector. Longer inputs mean more content per dimension, so early tokens are overwritten by later ones.

  2. What is teacher forcing, and what problem does it create?
    Answer

    Feeding the ground-truth previous token during training. It makes training fast and stable, but the model never practises recovering from its own mistakes — exposure bias.

  3. How does attention change the decoder's access to the input?
    Answer

    Instead of one summary vector, the decoder can query every encoder state and weight them per output step. The bottleneck becomes a soft lookup.

Build it in Colab

Runnable, NumPy-only, no setup: open the notebook in Colab · local copy. The cell prints numbers, not pictures — change one value and rerun to see what breaks.

import numpy as np
rng = np.random.default_rng(0)
def encode(tokens, dim=8):
    """Toy encoder: mean of token vectors, i.e. a fixed-size summary."""
    return rng.normal(size=(len(tokens), dim)).mean(axis=0)
for n in (4, 16, 64):
    s = encode(["w"] * n)
