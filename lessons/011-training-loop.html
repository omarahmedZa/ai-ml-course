The training loop

You can write the five-line loop and read a loss curve well enough to diagnose it.

Why this matters

The training loop is five moves repeated until the loss stops falling, and every model in the rest of this course runs it unchanged. Learn it once and experiments become edits to a single line.

It is also where most first runs die, for four reasons that are all visible in the curve. The exam version is pure counting: "50,000 examples, batch 250, eight epochs — how many parameter updates?" The project version is a loss flat at 0.693 on a binary task, because the model outputs 0.5 for everything and has not moved at all. Neither question needs the architecture; both need the loop.

The one core idea

The loop is a thermostat with a fixed routine: look at a batch, measure the error, find the slope, nudge every weight a little, clear the slate. Nothing clever happens here — the information is in the gradients, and the loop only decides how far to step.

In one line: forward, loss, backward, step, zero. With η = 0.05 and ∂L/∂w = −32, the update is w ← w − 0.05(−32) = w + 1.6.

How it actually works

for x, y in loader:          # one batch
    pred = model(x)          # forward
    loss = criterion(pred, y)
    loss.backward()          # gradients accumulated
    opt.step()               # w ← w − η∇w
    opt.zero_grad()          # reset, or gradients add up

Part 1 — Shuffle, then slice a batch

The loader permutes the dataset and hands you 32 or 100 rows at a time. Shuffling matters because consecutive examples are often correlated — sorted by class or by date — and a batch of one class produces a gradient for that class only. One pass over all 10,000 examples at batch 100 gives 100 slices. Why this part exists: without the shuffle the model learns the ordering of the file, and the loss oscillates with the sort order rather than with the data.

Part 2 — Forward: predict for the whole batch

pred = model(x) runs topic 9's forward pass on all rows at once and returns one prediction per example. For a batch of 100 with 10 classes that is a 100 × 10 matrix, not 100 separate calls. Why this part exists: the batch is where the speed comes from; a Python loop over examples would run the same maths a hundred times slower.

Part 3 — Loss: collapse the batch to one number

The criterion compares the 100 predictions with the 100 labels and averages, so loss is a single scalar with one gradient. Cross-entropy — the standard classification loss — at a predicted probability of 0.5 gives 0.693; at 0.9 it gives 0.105. Why this part exists: one number is what backward needs — a vector loss could not be minimised, because "smaller in every coordinate" is not a direction.

Part 4 — Backward fills a gradient per parameter

loss.backward() runs topic 10's sweep and writes .grad on every weight and bias. The values are accumulated into those slots rather than replacing them, which is a detail that matters in Part 6. For the single weight above, ∂L/∂w = −32 arrives in w.grad. Why this part exists: the gradients are the only thing that says which direction each of a million weights should move.

Part 5 — Step: move against the slope

opt.step() applies w ← w − η·∂L/∂w to every parameter, using one shared η — the learning rate, or step size. With η = 0.05 and a gradient of −32 the weight grows by 1.6. Too large an η overshoots the minimum and the loss climbs; too small and the run finishes before anything is learned. Why this part exists: the gradients give a direction but not a distance, and η is the only knob that supplies the distance.

Part 6 — Zero the gradients before the next batch

opt.zero_grad() sets every .grad back to zero so the next backward() starts clean. PyTorch adds by default, so skipping this makes step t use the sum of gradients from steps 1 to t. Why this part exists: without the reset the effective step size grows with every batch, and a run that was stable for 50 steps diverges at 200.

Part 7 — Repeat: epochs become steps

One epoch is one pass over the dataset, so steps = epochs × n / batch. Ten thousand examples at batch 100 for 20 epochs is 20 × 100 = 2,000 updates — and at batch 1,000 the same 20 epochs is only 200 updates. Why this part exists: "I trained for 20 epochs" says nothing until you know the batch size, and most "it learned nothing" reports are simply too few updates.

1. Sizing a run

10,000 training examples, 20 epochs, three batch sizes. The update count is the number that actually governs learning.

What to notice. The middle row is the usual starting point: 2,000 updates is enough for a small model to converge, and averaging 100 examples keeps each step's gradient quiet. The last row is 10× fewer updates and 10× less noise per step, which is why large batches need more epochs or a higher learning rate to reach the same place.

2. Three iterations on one weight

One weight, one fixed input x = 2, target y = 10, so pred = 2w and L = (2w − 10)². The gradient is 4(2w − 10). Start at w = 1 with η = 0.05 and run the loop by hand.

What to notice. The target weight is 5, because 2(5) = 10. Each iteration multiplies the error by 0.6 — 8 → 4.8 → 2.88 — so the loss falls geometrically and never quite reaches zero. Nothing here "decides" to stop; the loop simply ends when the epoch count runs out, or when the improvement per step drops below what you care about.

3. Where 0.693 comes from

Binary cross-entropy is −ln(p) for a positive example. The loss of a model that predicts the same probability for everything depends only on that probability.

Predicted pComputationLoss
0.5−ln 0.50.693
0.9−ln 0.90.105
0.1−ln 0.12.303

A flat 0.693 therefore means p = 0.5 everywhere: the model outputs the uniform prediction and has learned nothing about the input. Any model that answers 0.5 to every example lands on this number, whatever the true class balance, which is why it is the value to memorise.

The curve's shape is the diagnosis, and each shape has one action:

CurveDiagnosisAction
Falls, then risesOverfittingEarly stop, regularise
Spikes to NaNη too high÷10, add warmup
Dead flat at 0.693Uniform outputCheck learning rate, labels, zero_grad
Falls then plateaus highUnderfitMore capacity, decay η

What to notice. Two rows are learning-rate problems, which is why the first experiment is a ladder — η in {1e-2, 1e-3, 1e-4}. A factor-of-ten sweep finds the order of magnitude in three runs. The flat row is different: a loss that never leaves 0.693 is not slow, it is stationary.

The trap

Most common wrong mental model

"The optimizer resets itself each step, so zeroing is cosmetic." It feels right because every iteration prints the same loss and the code looks symmetric: one backward, one step.

Correction: .grad is a buffer that backward() adds into, so step t uses the sum of the gradients from steps 1 to t. The algorithm you are running is no longer gradient descent but a running sum, and its effective learning rate grows linearly with the step count.

The tell: the loss falls for a few dozen steps, then gets jumpy or turns to NaN while the data and architecture are unchanged — and the first batch always behaves. Accumulation is also deliberate in gradient accumulation, so check the intent before deleting the line: two micro-batches of 16 with one step() approximates one batch of 32, but only if zero_grad comes after the step.

Retrieval check

  1. 50,000 examples, batch size 250, 8 epochs. How many parameter updates?
    Answer

    50000/250 = 200 steps per epoch, × 8 = 1,600 updates. Epochs alone tell you nothing without the batch size.

  2. Loss is 0.693 and perfectly flat on binary cross-entropy. What is the model outputting, and name two causes.
    Answer

    Probability 0.5 for every input. Causes: learning rate far too high (weights oscillate), or a broken gradient path (missing activation, detached tensor, forgotten zero_grad).

  3. What does opt.zero_grad() prevent?
    Answer

    Accumulation. Without it, step t uses the sum of gradients from steps 1…t, so the effective learning rate grows over time and training destabilises.
